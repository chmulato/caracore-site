A Anatomia de um Rebaselining: Migrando Gigantes Legados para Java 11 e WildFly 26

10/01/2026 Por Christian Mulato

Introdução

A modernização de sistemas legados é frequentemente comparada a trocar os pneus de um carro em movimento. Mas quando se trata de migrar um sistema core empresarial – aquele que sustenta operações críticas de negócio – a analogia mais apropriada seria trocar o motor, a transmissão e o sistema de direção, tudo ao mesmo tempo, enquanto o veículo trafega a 100 km/h em uma rodovia movimentada.

Este artigo narra a experiência real de migrar um sistema de alta complexidade (codinome: Projeto Phoenix) de um ambiente tecnológico antigo para Java 11 e WildFly 26, enfrentando desafios que testaram não apenas competências técnicas, mas também resiliência, metodologia e capacidade de trabalhar sob pressão.

O Desafio da Baseline: Mais Que Código, Uma Sinfonia de Componentes

Quando falamos de baseline em projetos de software, a maioria dos profissionais pensa imediatamente em versões de código versionadas no Git ou em releases de pacotes perfeitamente etiquetados. Simples, direto, binário. Mas em migrações complexas de sistemas legados, a realidade é muito mais intrincada e nuançada.

Uma baseline verdadeira não é apenas um número de versão. É a sincronia perfeita entre três camadas fundamentais que precisam dançar em harmonia absoluta:

  • Infraestrutura: A versão específica do servidor de aplicação (WildFly 26), a JVM (Java 11), configurações de rede, certificados SSL/TLS precisamente configurados, variáveis de ambiente em cada servidor. Não basta que a JVM esteja instalada – ela precisa estar na versão certa, com os patches de segurança aplicados.
  • Backend: As bibliotecas Java (JPA, JAX-RS, Apache Wink, Apache Shiro), a estrutura de dados, integrações com sistemas externos, APIs REST que conversam com múltiplos parceiros. Cada dependência tem uma versão, cada versão tem quirks.
  • Frontend: O framework JavaScript (AngularJS 1.5), dependências NPM, sistema de build, estrutura modular. Uma mudança em um módulo frontend pode quebrar todo o processo de bootstrap.

O problema surge quando um componente de uma camada evolui sem que os demais acompanhem. É como ajustar o carburador de um motor antigo para funcionar com gasolina moderna – se o sistema de escape não suportar a nova combustão, se o catalisador não conseguir processar os novos resíduos, todo o sistema falha catastroficamente.

No Projeto Phoenix, a baseline herdada era um monumento à resiliência humana face ao caos. Trazia consigo anos de remendos, patches emergenciais e workarounds que se tornaram parte da "solução oficial". Desenvolvedores que saíram levaram conhecimento. Documentação desapareceu. O que restava eram camadas de decisões técnicas enterradas em código que ninguém entendia completamente. O desafio não era apenas migrar para tecnologias mais modernas – era desemaranhar essa teia desconcertante de dependências sem romper a continuidade operacional de um sistema que processava transações críticas 24/7.

O Caos do Frontend: Quando AngularJS 1.5 Se Recusa a Colaborar

O Erro Que Paralisa Tudo

Se você já trabalhou com AngularJS 1.5, provavelmente conhece aquele medo gelado na espinha quando vê o temido erro aparecer no console do navegador:

Uncaught Error: [$injector:modulerr] Failed to instantiate module app.module

É um erro que parece simples na superfície, quase enigmático. Mas pode ter dezenas de causas raiz diferentes, cada uma mais obscura que a anterior. No nosso caso específico, após semanas de investigação minuciosa, descobrimos que a causa subjacente era inconsistências de nomenclatura entre módulos e sub-módulos. O AngularJS, como muitos frameworks antigos, é notoriamente sensível a essas convenções:

  • camelCase para nomes de módulos em JavaScript (app.moduloFinanceiro)
  • kebab-case para nomes de arquivos e diretivas HTML (modulo-financeiro.js, <modulo-financeiro>)

A equipe anterior havia criado uma estrutura modular sofisticada onde módulos de negócio eram carregados dinamicamente em tempo de execução, com base nas permissões específicas do usuário logado. Era inteligente em teoria – segurança por design, bundle JavaScript otimizado. Mas na prática, diversos módulos referenciavam sub-módulos que nem sempre estavam presentes no bundle final. Dependendo do perfil de acesso do usuário, alguns módulos ficavam órfãos, apontando para dependências que não existiam.

A Estratégia de Graceful Degradation

A solução inicial – óbvia mas engenhosamente ingênua – seria garantir que todos os módulos estivessem sempre presentes, sem importar o perfil. Mas isso violava requisitos de segurança auditados (certos módulos simplesmente não podiam estar no bundle de usuários sem permissão) e aumentava desnecessariamente o tamanho do JavaScript enviado ao navegador (alguns usuários recebiam 40% de código que nunca execuariam).

A abordagem que adotamos foi muito mais elegante: Graceful Degradation através de módulos mock vazios. A ideia é simples, mas poderosa:

// Módulos vazios para evitar quebra de dependências
angular.module('app.moduloFinanceiro.desabilitado', []);
angular.module('app.moduloRH.desabilitado', []);
angular.module('app.moduloEstoque.desabilitado', []);

// Módulo principal com injeção condicional
angular.module('app.main', [
  'app.core',
  userHasPermission('FINANCEIRO') ? 'app.moduloFinanceiro' : 'app.moduloFinanceiro.desabilitado',
  userHasPermission('RH') ? 'app.moduloRH' : 'app.moduloRH.desabilitado',
  // ... outros módulos
]);

Esta estratégia garantiu que:

  • O bootstrap da aplicação nunca falha por falta de módulos, mesmo que um inteiro esteja ausente
  • Os módulos desabilitados não carregam lógica de negócio desnecessária, mantendo o bundle enxuto
  • O sistema é facilmente extensível para novos módulos condicionais sem modificar o core

Mas a grande lição que extraímos? Nunca subestime a importância de convenções de nomenclatura consistentes, por mais trivial que pareça. Horas preciosas de debugging foram gastas em uma noite de quinta-feira, rastreando um simples hífen onde deveria haver um underscore. O desenvolvedor que identificou o problema praticamente caiu da cadeira quando descobriu a causa raiz. Uma sequência de caracteres simples destruía todo um subsistema.

O Colapso do Backend: Quando Apache Wink e WildFly 26 Entram em Conflito Mortal

O Erro Fatal que Interrompe o Deploy

Logo após o sucesso inicial e celebrações contidas do frontend, o backend nos apresentou um desafio que parecia vindo de outro planeta – um erro tão obscuro que seus primeiros sintomas levaram a equipe inteira a um beco sem saída:

java.io.FileNotFoundException: META-INF/wink-alternate-shortcuts.properties
    at org.apache.wink.common.internal.registry.metadata.ClassMetadataCollector.collectMetadata
    at org.apache.wink.server.internal.DeploymentConfiguration.init

Deixe-me pintar o cenário: o Apache Wink 1.4 era o motor JAX-RS legado que orquestrava toda a infraestrutura de endpoints REST da aplicação. Um workhorse invisível que funcionava perfeitamente, sem questionamentos, no antigo JBoss AS 7 com Java 7. Mas quando o sistema tentava inicializar no WildFly 26, o motor simplesmente recusava-se a despertar. A aplicação entrava em estado de limbo – o servidor iniciava, mas o contexto da aplicação não conseguia se carregar, deixando toda a infraestrutura indisponível.

A Raiz do Conflito: Dois Motores JAX-RS na Mesma Pista

A investigação revelou um conflito fundamental: o WildFly 26 vem com seu próprio motor JAX-RS nativo integrado (RESTEasy), e a presença simultânea de dois frameworks diferentes disputando o controle da mesma especificação causava conflitos de classloader em cascata.

O problema específico do wink-alternate-shortcuts.properties ocorria em uma sequência de eventos que parecem triviais isoladamente, mas catastróficos em conjunto:

  1. O Apache Wink procurava este arquivo de configuração no classpath durante a inicialização
  2. O WildFly 26 empacotava suas próprias bibliotecas JAX-RS em um módulo isolado, com seu próprio classloader
  3. O classloader do Wink não tinha permissão e não conseguia acessar recursos de módulos isolados do WildFly

Era um impasse clássico de arquitetura de aplicação: dois sistemas tentando controlar o mesmo espaço, com cada um invisível para o outro.

A Solução: Isolamento Cirúrgico via jboss-deployment-structure.xml

Após noites de investigação analisando logs enigmáticos, a solução emergiu: precisávamos instruir explicitamente o WildFly para excluir seus próprios módulos JAX-RS do classpath da aplicação, forçando a aplicação a usar o Apache Wink enlatado:

<?xml version="1.0"?>
<jboss-deployment-structure xmlns="urn:jboss:deployment-structure:1.2">
    <deployment>
        <!-- Exclusão dos módulos JAX-RS nativos do WildFly -->
        <exclusions>
            <module name="org.jboss.resteasy.resteasy-jaxrs" />
            <module name="org.jboss.resteasy.resteasy-jackson-provider" />
            <module name="javax.ws.rs.api" />
        </exclusions>
        
        <!-- Dependências explícitas necessárias -->
        <dependencies>
            <module name="org.apache.commons.lang" />
            <module name="org.slf4j" />
        </dependencies>
    </deployment>
</jboss-deployment-structure>

Este arquivo deve ser colocado em WEB-INF/jboss-deployment-structure.xml dentro do WAR.

Adicionalmente, foi necessário empacotar o Apache Wink e todas as suas dependências diretamente no WEB-INF/lib da aplicação, garantindo total isolamento do ambiente do servidor. Mas aqui vem o detalhe crucial: quando você força a exclusão de módulos nativos do WildFly, está basicamente dizendo "não confio no que você oferece, vou trazer o meu próprio". Isso significa que o WAR é literalmente autocontido – tudo o que precisa para funcionar está dentro dele.

Lição aprendida: Em servidores de aplicação modernos, o isolamento de bibliotecas não é opcional – é mandatório. A era dos classpath globais e das "bibliotecas compartilhadas" ficou no passado. Cada aplicação precisa ser uma ilha de tecnologia autossustentável.

A Última Milha: Segurança, Identidade e a Cadeia de Confiança SSL

O Papel Crítico do Apache Shiro e os Desafios de Autenticação

O Apache Shiro era (e ainda é) o framework responsável pela autenticação e autorização na aplicação. Sua integração com LDAP corporativo e sistemas de Single Sign-On (SSO) funcionava como o guardião de acesso, decidindo quem podia fazer o quê, quando e onde. Na migração para Java 11 e WildFly 26, este guardião precisava ser reconfigurado para um novo contexto operacional.

Os desafios que emergiram foram múltiplos e entrelaçados:

  • Mudanças na API de segurança do Java 11: Algoritmos de criptografia considerados fracos foram deprecados. Bibliotecas de segurança foram refatoradas. A JVM 11 é mais rigorosa sobre quais provedores de segurança (security providers) são permitidos.
  • Configurações de realm LDAP: O Shiro precisou ser reconfigurado para trabalhar com o novo contexto de segurança do WildFly, que introduziu suas próprias camadas de abstração de segurança (PicketBox, depois Undertow).
  • Session management: A forma como o WildFly 26 gerencia sessões HTTP difere significativamente do JBoss AS 7. Timeout, serialização, persistência – tudo mudou.

A configuração do shiro.ini precisou ser ajustada para garantir compatibilidade entre versões:

[main]
# Configuração do LDAP Realm
ldapRealm = org.apache.shiro.realm.ldap.JndiLdapRealm
ldapRealm.userDnTemplate = uid={0},ou=users,dc=empresa,dc=com
ldapRealm.contextFactory.url = ldaps://ldap.empresa.com:636
ldapRealm.contextFactory.systemUsername = cn=app_user,dc=empresa,dc=com
ldapRealm.contextFactory.systemPassword = ${LDAP_PASSWORD}

# Crucial para Java 11+
ldapRealm.contextFactory.environment[java.naming.ldap.factory.socket] = com.empresa.security.TrustAllSSLSocketFactory

A Importância Crítica do cacerts: O Alicerce da Confiança Digital

Mas o problema mais insidioso surgiu nas comunicações HTTPS com sistemas externos. A aplicação precisava se comunicar com múltiplas APIs externas usando SSL/TLS seguro, mas começou a falhar com um erro que parecia vindo de outro mundo:

javax.net.ssl.SSLHandshakeException: sun.security.validator.ValidatorException: 
PKIX path building failed: unable to find valid certification path to requested target
  at sun.security.ssl.Alert.createSSLException(Alert.java:131)
  at sun.security.ssl.TransportContext.fatal(TransportContext.java:379)

Estes erros indicavam algo fundamental: o truststore do Java 11 – o arquivo especial chamado cacerts localizado em $JAVA_HOME/lib/security/cacerts – não confiava nos certificados SSL dos servidores com os quais a aplicação se comunicava.

O cacerts é como o "livro de confissões" da JVM. Ele contém uma lista de certificados raiz (CAs) que a JVM considera confiáveis. Quando você tenta estabelecer uma conexão HTTPS com um servidor, a JVM verifica se o certificado desse servidor foi assinado por uma CA confiável. Se não, a conexão é bloqueada com erro de validação.

A solução envolveu um processo metodológico em três etapas:

  1. Exportar os certificados dos servidores de destino usando OpenSSL:
openssl s_client -connect api.externa.com:443 -showcerts > certificado.pem
  1. Importar no cacerts do Java 11 usando a ferramenta keytool (a mala direta de segurança da JVM):
keytool -import -alias api_externa -keystore $JAVA_HOME/lib/security/cacerts -file certificado.pem
# Você será solicitado a fornecer a senha do keystore
# Senha padrão do JDK: changeit
  1. Reiniciar o WildFly para que a JVM recarregue o truststore na memória

Ponto de atenção crítico: Em ambientes containerizados (Docker/Kubernetes), este processo não pode ser manual. Cada instância da aplicação precisa ter o cacerts pré-configurado. A solução é automatizar isso no Dockerfile ou via ConfigMaps (no Kubernetes), garantindo que quando o container for iniciado, ele já tenha todos os certificados necessários. Falhar em fazer isso resulta em aplicações "fantasma" que funcionam localmente mas falham em produção.

Lições Aprendidas: A Arte de Gerenciar Expectativas e Rituais de Passagem

1. Comunique-se com Transparência: O Custo Real da Modernização

Delivery Managers e stakeholders de negócio frequentemente subestimam a complexidade de migrações legadas. A expectativa inicial de "algumas semanas" pode facilmente se transformar em meses quando incompatibilidades de baixo nível emergem do nada, aparentemente do vácuo. Cada descoberta leva a investigações que consomem dias inteiros.

Estratégias eficazes que implementamos:

  • Dashboards visuais por camada: Criamos painéis mostrando progresso separado para Infraestrutura, Backend e Frontend. Cada camada tinha suas próprias métricas e marcos. Isso permite que não-técnicos entendam que "o frontend está 90% pronto, mas o backend é 45%" não são números mágicos, mas refletem complexidades reais.
  • Changelog técnico acessível: Mantemos um arquivo versionado chamado MIGRATION_LOG.md que listava, para cada semana, quais problemas foram descobertos, quais foram resolvidos e quais ainda estavam em investigação. Isso evita o efeito "foi o meu erro?" quando o stakeholder pergunta por que o progresso é lento.
  • Marcos intermediários tangíveis: Em vez de "Migração do Backend", criamos marcos como "Baseline de Login", "Baseline de Relatórios", "Baseline de Integração com Sistemas Externos". Cada um poderia ser testado e validado independentemente.

2. O Ritual Sagrado: Limpeza de Cache Entre Deploys

Aqui vem um conhecimento que raramente aparece em tutoriais, mas que é absolutamente crítico em WildFly. Em todos os deploys, sem exceção, sem atalhos, execute este ritual:

cd $WILDFLY_HOME
rm -rf standalone/tmp/*
rm -rf standalone/data/*
rm -rf standalone/deployments/*.deployed
rm -rf standalone/deployments/*.failed

Por que? Estes diretórios acumulam artefatos que o WildFly às vezes "esquece" de limpar:

  • tmp/: Classloaders já compilados, bytecode em cache, arquivos temporários de upload que ficam órfãos
  • data/: Cache de sessões, objetos serializados de requisições anteriores que às vezes são desserializados incorretamente
  • deployments/: Marcadores de estado de deploy (`.deployed`, `.failed`) que dizem ao WildFly "este WAR já foi processado"

Falhar em limpar esses diretórios é a causa #1 de problemas "fantasma" que aparecem e desaparecem misteriosamente entre deploys. Você redeploya a aplicação, o código está correto, mas o erro continua aparecendo. Você olha para o desenvolvedor que fez o deploy e pergunta "você limpou o cache?", e quase sempre a resposta é não.

3. Documente os Workarounds, Mas Planeje Sua Eliminação

Cada workaround é uma dívida técnica que precisa ser honrada eventualmente. Durante a migração do Projeto Phoenix, mantivemos um arquivo versionado chamado TECH_DEBT.md que residia junto com o código no repositório Git. Cada workaround tinha uma entrada estruturada:

## TD-2024-001: Exclusão de módulos JAX-RS do WildFly
**Status:** Ativo
**Razão:** Conflito entre Apache Wink 1.4 e RESTEasy nativo do WildFly
**Workaround:** Arquivo jboss-deployment-structure.xml que exclui módulos JAX-RS
**Impacto:** Aplicação depende de Apache Wink versionado, bloqueando futuras migrações para JAX-RS
**Plano de eliminação:** Refatorar todos os endpoints para JAX-RS 2.1 nativo (estimado Q3/2026)
**Prioridade:** Alta - bloqueia atualização de WildFly

## TD-2024-002: Socket Factory customizado para LDAPS
**Status:** Ativo
...

Isso serve dois propósitos críticos:

  • Contexto futuro: Garantir que a equipe que vem depois não perca contexto sobre por que certas decisões foram tomadas
  • Trackeamento de débito: Permitir que o gestor de projeto saiba exatamente quais são os débitos técnicos que reduzem a qualidade do código

4. Automatize Tudo Que For Repetitivo: Erros Humanos Custam Caro

Scripts de deploy, validação de ambiente, testes de fumaça – tudo deve ser automatizado. Humanos cometem erros. Computadores executam instruções sem discussão. No Projeto Phoenix, criamos um script chamado pre-deploy-check.sh que validava, antes de qualquer deploy:

  • Versão do Java: Exatamente Java 11.0.x+, nenhuma outra
  • Variáveis de ambiente obrigatórias: JAVA_HOME, WILDFLY_HOME, LDAP_PASSWORD, DATABASE_URL
  • Conectividade com sistemas externos: LDAP acessível? APIs externas respondendo? Banco de dados conectado?
  • Presença de certificados no cacerts: Validava que todos os certificados necessários foram importados
  • Limpeza de diretórios temporários: Executava automaticamente a limpeza de tmp/, data/, deployments/

Este script evitou dezenas de deploys falhados causados por "esquecimentos humanos" – variáveis de ambiente não configuradas, JAVA_HOME apontando para a versão errada, certificados faltando no cacerts. A máquina não esquece. O humano esquece.

Conclusão: A Estabilização de Legados é Uma Arte, Não Uma Ciência

Migrar sistemas legados não é uma corrida de 100 metros – é uma maratona em terreno acidentado, com obstáculos que aparecem conforme você avança. Requer uma mistura delicada de habilidades que poucas pessoas possuem simultaneamente:

  • Paciência para investigar erros obscuros em frameworks de 2010, em documentação desaparecida, em código escrito por pessoas que já saíram da empresa
  • Método
  • Resiliência para lidar com expectativas frequentemente desalinhadas entre negócio e tecnologia, com prazos apertados que não consideram a realidade técnica
  • Pragmatismo para aceitar que nem toda solução será elegante ou bonita – às vezes você precisa de um workaround feio que funciona, desde que esteja documentado

O Projeto Phoenix nos ensinou uma lição fundamental: a verdadeira baseline não está nas linhas de código ou nos números de versão. Está na coordenação harmoniosa entre todas as camadas da aplicação – infraestrutura, backend e frontend dançando em sincronia. Quando essa sincronia é alcançada, o sistema legado finalmente renasce, não como uma réplica descartável da tecnologia antiga, mas como um sistema estável, documentado e pronto para a próxima evolução.

E quando tudo funcionar perfeitamente após a migração, quando os testes passarem e a aplicação estiver em produção processando transações sem problemas? Lembre-se: sempre limpe o cache antes de comemorar. Porque há sempre aquele erro fantasmagórico esperando para aparecer se você não o fizer.
