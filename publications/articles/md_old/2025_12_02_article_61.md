## Parte I: O Desafio do E-commerce nas Cidades do Interior

### O Cenário: Campo Largo e o Brasil que Cresce Online

Campo Largo, município paranaense com aproximadamente 140 mil habitantes, localizado a 30 km de Curitiba, representa perfeitamente o novo perfil de consumo digital brasileiro. Não é mais a capital que dita sozinha as regras do e-commerce — cidades de médio porte, com população entre 50 mil e 200 mil habitantes, tornaram-se epicentros de uma revolução silenciosa: **a compra online com retirada local**.

### Por Que a Retirada Local Importa?

Dados recentes mostram que em cidades como Campo Largo, São José dos Pinhais (PR), Maricá (RJ), Várzea Grande (MT) e dezenas de outras regiões metropolitanas, até **35% dos consumidores online preferem retirar suas encomendas pessoalmente**. As razões são múltiplas:

1. **Desconfiança com entrega residencial**: Medo de roubo de pacotes deixados na porta
2. **Flexibilidade de horário**: Retirar no caminho do trabalho ou aos finais de semana
3. **Economia de frete**: Muitos marketplaces oferecem desconto para retirada
4. **Gratificação instantânea**: "Comprei online, mas quero hoje"
5. **Verificação imediata**: Possibilidade de conferir o produto antes de sair da loja

### O Problema Técnico que Ninguém Vê

Aqui mora o desafio: **como gerenciar centenas de consultas simultâneas ao estoque quando 200 pessoas estão, ao mesmo tempo, verificando se seu pedido chegou?**

Imagine o cenário:

- **Segunda-feira, 18h30**: Horário de saída do trabalho
- **Centro de Distribuição**: 450 pedidos aguardando retirada
- **Clientes consultando**: 180 pessoas acessando o sistema simultaneamente
- **Operadores internos**: 8 atendentes processando retiradas
- **Integrações externas**: Mercado Livre, Shopee e marketplaces consultando status a cada 2 minutos

**Resultado sem otimização**: Cada consulta acessa o banco de dados. 180 usuários × 3 consultas por acesso = **540 queries ao banco em menos de 1 minuto**. O sistema trava. Clientes desistem. Operadores perdem tempo esperando telas carregarem.

### A Matemática do Caos

Vamos aos números de uma operação típica em cidade média:

**Volume Diário**:

- 500 pedidos recebidos/dia
- 300 retiradas realizadas/dia
- 180 consultas simultâneas no pico (18h-19h)
- 12 operadores usando o sistema

**Sem cache (acesso direto ao banco)**:

- Tempo médio de query: 200ms
- Consultas por usuário: 3 (mapa de estoque + detalhes + validação)
- **Total no pico**: 180 usuários × 3 queries × 200ms = **108 segundos de processamento**
- Considerando concorrência: **usuários esperam 8-12 segundos por tela**

**Impacto no negócio**:

- Abandono de consulta: ~40% (usuários desistem após 5s)
- Operadores ociosos: 30% do tempo esperando sistema
- Custos de servidor: 3x maiores para suportar carga
- Experiência do cliente: **péssima**

### Por Que Bancos de Dados Relacionais Sofrem Aqui?

PostgreSQL, MySQL e outros bancos SQL são incríveis para **consistência e integridade**. Mas quando o cenário é:

- Muitas **leituras**, poucas escritas (90% consultas, 10% atualizações)
- Dados que **mudam pouco** ao longo de minutos (estoque não altera a cada segundo)
- Necessidade de **resposta imediata** (usuário não espera 5 segundos)

...os bancos relacionais mostram limitações:

- **Lock de tabelas** em operações concorrentes
- **Índices lentos** quando há milhões de registros
- **Rede adicional**: latência entre aplicação e banco
- **CPU intensiva**: cada query precisa parsear SQL, montar plano de execução

### A Busca por uma Solução Real

Não adianta "comprar um servidor mais potente". O problema é **arquitetural**. Precisávamos de:

1. **Cache inteligente**: Armazenar dados consultados frequentemente na memória
2. **Invalidação automática**: Atualizar cache quando estoque muda (item retirado, chegada de novo lote)
3. **Distribuição**: Funcionar em múltiplos servidores (Tomcat e WildFly rodando juntos)
4. **Simplicidade**: Desenvolvedores conseguem manter sem dor de cabeça
5. **Custo baixo**: Não gastar R$ 5.000/mês em infraestrutura

**E foi aí que o Redis entrou na história.**

## Parte II: Redis — A Solução que Transformou Nossa Arquitetura

### O Que É Redis? (Explicação para Leigos)

Imagine sua geladeira como um banco de dados. Quando você quer um suco:

- **Sem cache (ir ao supermercado)**: Você dirige 10 minutos, procura o suco, paga, volta. **Total: 25 minutos**.
- **Com cache (geladeira)**: Você abre a geladeira e pega o suco. **Total: 10 segundos**.

**Redis é a "geladeira" do nosso software.** 

Tecnicamente, é um **banco de dados em memória RAM** (não em disco rígido). Dados ficam prontos para acesso instantâneo. Como RAM é **1000x mais rápida que disco SSD**, as respostas são medidas em **milissegundos**, não segundos.

### Por Que Redis e Não Outras Soluções?

Avaliamos 4 alternativas:

| Solução | Prós | Contras | Decisão |
|---------|------|---------|---------|
| **Memcached** | Simples, rápido | Sem persistência, sem estruturas complexas | ❌ Muito básico |
| **Hazelcast** | Java-native, distribuído | Pesado (200MB+ RAM), complexo | ❌ Overkill |
| **EhCache** | Integrado ao app | Não compartilha entre servidores | ❌ Não serve para Tomcat + WildFly |
| **Redis** | Rápido, leve, Pub/Sub, persistência opcional | Requer servidor separado | ✅ **Escolhido** |

### A Arquitetura que Implementamos

```text
┌─────────────────────────────────────────────────────────────┐
│                     USUÁRIOS (180 simultâneos)              │
└────────────┬────────────────────────────────────────────────┘
             │
             ▼
┌─────────────────────────────────────────────────────────────┐
│              Tomcat (9090) + WildFly (8080)                 │
│  ┌──────────────────────────────────────────────────────┐   │
│  │  1. Recebe request: "Mostrar mapa de estoque"        │   │
│  │  2. Consulta Redis: "Mapa existe em cache?"          │   │
│  └──────────────────────────────────────────────────────┘   │
└────────────┬─────────────────────────────────┬──────────────┘
             │                                 │
             │ Cache HIT (95%)                 │ Cache MISS (5%)
             │ 2ms                             │ 200ms
             ▼                                 ▼
    ┌────────────────┐              ┌────────────────────────┐
    │  REDIS (6379)  │              │  PostgreSQL (5432)     │
    │  Cache Layer   │◄─────────────┤  Banco de Dados        │
    │  - Mapa: 15s   │  Atualiza    │  - Pedidos             │
    │  - KPIs: 2min  │  cache após  │  - Estoque             │
    │  - Lead: 5min  │  query       │  - Posições            │
    └────────────────┘              └────────────────────────┘
             ▲
             │ Pub/Sub: "Estoque mudou!"
             │ (Invalida cache em TODOS os servidores)
             │
    ┌────────────────────────────────────────┐
    │  Operador retira pedido → Pub/Sub      │
    └────────────────────────────────────────┘
```

### Os 3 Pilares da Nossa Implementação

#### 1. Cache com TTL (Time To Live)

Cada tipo de dado tem um "prazo de validade":

```java
// Mapa de estoque: atualiza a cada 15 segundos
REDIS_TTL_MAPA = 15s

// KPIs do dashboard: atualiza a cada 2 minutos
REDIS_TTL_KPIS = 120s

// Lead time médio: atualiza a cada 5 minutos
REDIS_TTL_LEAD_TIME = 300s

// Sessão do usuário: expira em 30 minutos de inatividade
REDIS_TTL_USER_SESSION = 1800s
```

**Por que isso importa?**  
Dados de estoque não precisam ser real-time ao nível de milissegundo. Se um item foi retirado há 3 segundos e o cache ainda não atualizou, **não há problema crítico**. O cliente vai clicar em "atualizar" e pegar a versão mais recente.

#### 2. Pub/Sub para Invalidação Inteligente

**O problema**: Temos 2 servidores (Tomcat e WildFly). Se Tomcat processa uma retirada e atualiza o cache, WildFly fica com dados desatualizados.

**A solução**: Redis Pub/Sub (Publish/Subscribe)

```java
// Quando operador retira um pedido:
1. Atualiza PostgreSQL (banco principal)
2. Publica mensagem: "Estoque da posição A7 mudou!"
3. TODOS os servidores escutando o canal recebem a mensagem
4. Cada servidor invalida seu cache local daquela posição
5. Próxima consulta: busca PostgreSQL novamente e recache
```

**Resultado**: Sincronização entre servidores em **menos de 50ms**.

#### 3. Fallback Gracioso

```java
try {
    // Tenta buscar do Redis
    String cacheData = redis.get("estoque:mapa");
    if (cacheData != null) {
        return cacheData; // Cache HIT - 2ms
    }
} catch (RedisConnectionException e) {
    // Redis caiu? Não tem problema!
    logger.warn("Redis indisponível, consultando banco diretamente");
}

// Cache MISS ou Redis offline: busca PostgreSQL
String data = database.query("SELECT * FROM posicao WHERE tenant_id = 1");
redis.set("estoque:mapa", data, 15); // Tenta cachear
return data; // 200ms, mas funciona
```

**Resiliência**: Se Redis cair (manutenção, bug, etc), **sistema continua funcionando**. Só fica mais lento, mas não quebra.

### Os Números que Provam o Sucesso

**Antes do Redis** (acesso direto ao PostgreSQL):

- Tempo médio de resposta: **1.200ms** (1,2 segundos)
- Pico de latência: **8.500ms** (8,5 segundos)
- Queries ao banco/minuto: **540**
- Taxa de abandono: **42%**
- CPU do banco: **78%** (constantemente alto)

**Depois do Redis** (cache em 95% dos acessos):

- Tempo médio de resposta: **85ms** (0,085 segundos) → **14x mais rápido**
- Pico de latência: **350ms** → **24x melhoria**
- Queries ao banco/minuto: **27** → **95% de redução**
- Taxa de abandono: **8%** → **redução de 80%**
- CPU do banco: **12%** → **sistema relaxado**

### Lições para Outras Operações

Nossa experiência com Redis no CaraCore Hub nos ensinou:

1. **Cache não é "tecnologia de startupzão"**: Empresas de qualquer porte que têm **>100 usuários simultâneos** se beneficiam
2. **Não precisa ser perfeito**: Dados com 10-30 segundos de defasagem são **aceitáveis em 90% dos casos**
3. **Comece pequeno**: Não cachear tudo de uma vez. Começamos com o mapa de estoque (maior dor), depois expandimos
4. **Monitore sempre**: Redis tem métricas integradas. Importante ver hit rate (% de cache hits vs misses)
5. **Documente TTLs**: Cada time precisa entender por que cada cache expira em X segundos
